# Basketball Empire Architecture v0.1

Status: Approved for MVP implementation

## Goals

- Run a complete Basketball Empire match for 2–4 players in a shared online room.
- Keep game decisions authoritative on the server.
- Synchronize room and match state in near real time.
- Keep the rules engine independent from HTTP and UI code.
- Require no database or third-party runtime package for the first private-play release.

## Runtime

- Node.js HTTP server
- Server-Sent Events (SSE) for server-to-browser state updates
- JSON `POST` endpoints for player actions
- Static HTML, CSS, and browser JavaScript client
- In-memory room repository for the private MVP
- Node built-in test runner for unit and integration tests

## Modules

### Rules engine: `src/game.js`

Pure state transitions for board creation, room players, match start, dice movement, team signing, revenue, turn progression, roster upgrades, mortgages, and final scoring.

### Room service: `src/room-service.js`

Creates room codes and private player tokens, validates player actions, owns active room state, and publishes state changes.

### HTTP server: `src/server.js`

Serves static assets and exposes room/action APIs. SSE clients receive sanitized public room snapshots; private player tokens are never included in snapshots.

### Browser client: `public/`

Provides the lobby, four-player identity display, board, action controls, asset panels, game log, responsive layout, and reconnect behavior.

## Trust and synchronization

- Dice are generated by the server.
- Every mutation requires the room code and private player token.
- Only the active player can perform turn actions.
- Each accepted mutation increments a room revision and broadcasts a new snapshot.
- Reconnecting clients receive the latest authoritative snapshot.

## MVP persistence boundary

Rooms live in memory and are lost when the server restarts. Persistent accounts, database storage, public matchmaking, and anti-abuse infrastructure are outside v0.1.

## Quality gates

- Rules-engine tests cover core state transitions and invariants.
- Room-service tests cover four-player limits, readiness, authorization, and name initials.
- HTTP integration tests cover room creation and joining.
- The complete test suite must pass before implementation is considered ready.
- The UI must remain usable at desktop and mobile widths.
